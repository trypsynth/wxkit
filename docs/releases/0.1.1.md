WxKit 0.1.1 fixes methods whose id 0.1.0 gave in the wrong place. Install it with `dotnet add package WxKit`.

## Fixes that may need code changes

0.1.x releases only fix bugs and add what needs no code changes. This fix is the exception, because the methods it fixes couldn't be used as they were meant to be: a rule for making windows, which moves a new window's id last and lets it default to any id, was applied to methods where the id names what the call is about. So `MenuBar.Check(bool check, int id = -1)` checked no item when the id was left out, and took its arguments in the opposite order from wxWidgets'. These methods take their id first now, and require it, as in wxWidgets:

- `MenuBar.Check(int id, bool check)`, `EnableItem(int id, bool enable)`, `SetLabel(int id, string label)`, and `SetHelpString(int id, string helpString)`, and `IsChecked`, `IsItemEnabled`, `GetLabel`, and `GetHelpString`, which take only the id.
- `ToolBar.SetDropdownMenu(int id, Menu menu)`, `SetToolNormalBitmap(int id, Bitmap bitmap)`, and `SetToolDisabledBitmap(int id, Bitmap bitmap)`, and `FindById` and `FindControl`, which take only the id.
- `Dialog.AddMainButtonId` and `IsMainButtonId`, and `Frame.ProcessCommand`.
- `Window.UnreserveControlId(int id, int count = 1)`.

A call that gave the id goes on working once its arguments are swapped, such as `bar.Check(true, id)` becoming `bar.Check(id, true)`. A call that left the id out never did what it meant.

Constructors, and methods that make a window, such as `Frame.CreateStatusBar` and `BitmapButton.NewCloseButton`, keep their optional id last.

## Inside WxKit

- `TreeListCtrl.Selections` is generated, like WxKit's other lists, rather than written by hand in C++.
- The generator's naming tables refuse a word they already have, rather than letting a second entry replace the first unnoticed.

WxKit is heavily vibe coded. If AI-written code is a dealbreaker for you, this is not the project for you.
