WxKit 0.1.1 fixes methods whose id 0.1.0 gave in the wrong place. Install it with `dotnet add package WxKit`.

## Fixes that may need code changes

0.1.x releases only fix bugs and add what needs no code changes. This fix is the exception, because the methods it fixes couldn't be used as they were meant to be: a rule for making windows, which moves a new window's id last and lets it default to any id, was applied to methods where the id names what the call is about. So `MenuBar.Check(bool check, int id = -1)` checked no item when the id was left out, and took its arguments in the opposite order from wxWidgets'. These methods take their id first now, and require it, as in wxWidgets:

- `MenuBar.Check(int id, bool check)`, `EnableItem(int id, bool enable)`, `SetLabel(int id, string label)`, and `SetHelpString(int id, string helpString)`, and `IsChecked`, `IsItemEnabled`, `GetLabel`, and `GetHelpString`, which take only the id.
- `ToolBar.SetDropdownMenu(int id, Menu menu)`, `SetToolNormalBitmap(int id, Bitmap bitmap)`, and `SetToolDisabledBitmap(int id, Bitmap bitmap)`, and `FindById` and `FindControl`, which take only the id.
- `Dialog.AddMainButtonId` and `IsMainButtonId`, and `Frame.ProcessCommand`.
- `Window.UnreserveControlId(int id, int count = 1)`.

A call that gave the id goes on working once its arguments are swapped, such as `bar.Check(true, id)` becoming `bar.Check(id, true)`. A call that left the id out never did what it meant.

Constructors, and methods that make a window, such as `Frame.CreateStatusBar` and `BitmapButton.NewCloseButton`, keep their optional id last.

## Other fixes

WxKit's tests now run under AddressSanitizer and UndefinedBehaviorSanitizer, which found undefined behavior that could crash an application or misbehave depending on the compiler. None of these fixes changes how WxKit is called.

- Copying a `FontData`, as a font dialog does with the one it's given, read uninitialized memory in wxWidgets.
- `RichMessageDialog` called into wxWidgets' message dialog before it was made.
- `PrintPreview.Show` cast the preview to a class it wasn't yet, and a printout's preview was the wrong object.
- A virtual `ListCtrl` or `ListView` that called the base `OnGetItemText` and the other base members did so through a cast to a class the control isn't.

The first three are in wxWidgets, which WxKit now patches until a wxWidgets release has the fixes. Each patch is also a pull request to wxWidgets: [#27399](https://github.com/wxWidgets/wxWidgets/pull/27399), [#27400](https://github.com/wxWidgets/wxWidgets/pull/27400), and [#27401](https://github.com/wxWidgets/wxWidgets/pull/27401).

## Inside WxKit

About a quarter of the C++ that WxKit wrote by hand is now generated from wxWidgets' interface headers instead, which keeps exceptions from escaping and types matching:

- The desktop's free functions, such as `Desktop.Bell`, and the classes that aren't wxObjects, such as `Display`, `UIActionSimulator`, `SingleInstanceChecker`, `WindowDisabler`, and `Timer`.
- The sizer, toolbar, window, and menu members that WxKit's own classes wrap to track who owns what.
- The C++ that lets .NET override wxWidgets' virtual members, for `Printout`, `Accessible`, and the data view models, which `ListCtrl` shares.
- `TreeListCtrl.Selections`, which is generated, like WxKit's other lists.

The C# that calls the C++ WxKit still writes by hand is generated from its header too, and the generator fails on a hand-written function that calls wxWidgets outside the guard that turns its exceptions into errors. CI also runs clang-tidy on the hand-written C++. The generator's naming tables refuse a word they already have, rather than letting a second entry replace the first unnoticed.

WxKit is heavily vibe coded. If AI-written code is a dealbreaker for you, this is not the project for you.
