# Testing

GUI code needs a display, an event loop, and, on macOS, the process's main thread. This document describes WxKit's tests and how they run anyway.

## Test projects and checks

- `tests/WxKit.Tests` creates real windows and checks the managed API against real wxWidgets: lifetime, events, threading, strings, accessibility, and the rest. Its `PublicApiTests` compares every public type and member, with nullability and defaults, to the snapshot in `PublicApi.txt`, leaving out the raw interop layer, so an API change shows up in review. To accept a change, run `$env:WXKIT_UPDATE_API = 1; dotnet test --project tests/WxKit.Tests -- --filter-class *PublicApiTests`, which rewrites the file.
- `tests/WxKit.Generator.Tests` checks the generator's Doxygen reader, binder, naming, and constants against trimmed Doxygen XML. `tests/WxKit.Build.Tests` checks the MSBuild tasks and targets in `src/WxKit/build`, which extract translatable strings and check and update catalogs. Neither needs a GUI.
- `scripts/test-aot.ps1` publishes each sample with Native AOT and runs it with `--smoke`, which shows its window, waits for the event loop to start, and exits. It fails on a trim or AOT warning, on a `wxkitnative` library left beside the executable, and, on macOS, on an invalid `Info.plist` or signature in the app bundle. This catches link problems no other test can. The library itself treats every warning as an error, so analyzer warnings fail its build.

Run any project with `dotnet test --project <folder>`, and the smoke test with `./scripts/test-aot.ps1`. `global.json` opts in to running `dotnet test` through Microsoft.Testing.Platform. CI runs the generator tests on `win-x64` only, and everything else on every runtime, as [Building and packaging](building-and-packaging.md) describes.

## Running tests on the main thread

wxWidgets needs every GUI call on one thread, which on macOS must be the main thread, but test frameworks run tests on worker threads. The tests use xUnit v3, whose test projects are executables, and `WxKit.Tests` turns off xUnit's generated entry point with `XunitAutoGeneratedEntryPoint` for a custom `Main`, in `Program.cs`, that runs the tests on the main thread's event loop. `Main` calls `Application.Run`, which gives wxWidgets the main thread, and starts xUnit's runner on a thread of its own: Microsoft.Testing.Platform under `--server`, which is how `dotnet test` starts it, and xUnit's console runner otherwise. When the runner finishes, `Application.Exit` ends the event loop, so a leaked window cannot keep the run going. A hidden frame keeps the loop alive between tests, and tests do not run in parallel, as `xunit.runner.json` sets, because they share the GUI thread. `SingleInstanceTests` also starts the test executable as a second copy of an application, which `Main` checks for first.

Each test hands its body to the GUI thread through the `Gui` helper:

- `Gui.Run` posts the body, which can be async, waits for it, and returns its result.
- `Gui.WithFrame` runs the body with a new frame, and destroys the frame afterwards if the body did not.
- `Gui.WaitUntil` runs the event loop until a condition holds, for work wxWidgets does at idle time.
- An exception that escapes an event handler while a body runs fails the test, unless the test takes it with `Gui.TakeUnhandled`. So does a failed wxWidgets assertion, unless the test takes it with `Gui.TakeAssertions`.

## Platform-specific tests

Some tests only mean something on Windows, and skip elsewhere with `Assert.SkipUnless`, so a skipped count is expected on Linux. Tests that click a button or choose a menu item send, with `SendMessage`, the `WM_COMMAND` notification the control would send its parent, which is processed, events included, before `SendMessage` returns. `BM_CLICK` is not used, because it only works on a button in the active window. Tests of `Accessible` read a window through MSAA as a screen reader does: `Msaa.Of` gets the window's own `IAccessible`, so a test can check the name, role, state, or child count its `Accessible` answered.

The other tests avoid what only one platform does. For example, Windows paints a window during `Update`, and GTK on its next frame, so a painting test waits for the paint while the event loop runs.

## Real input

`InputTests` sends real input through `UIActionSimulator`: a click on a button, text typed into a text control, and a menu item's shortcut. The input goes to the foreground window, as a user's does, so each test first makes its frame active and focuses the control, and on Windows also requires the frame to be the foreground window, since a window can be its thread's active one while another application's is in front. When the system will not do that, or a probe shows that simulated input does not arrive at all, as on GitHub's Windows runners, the test is skipped rather than failed. Windows sends the input with `SendInput`, and Linux with the XTest extension, which Xvfb has. macOS only lets an application send input with the accessibility permission, so the tests skip there.

## Displays and limits

Windows and macOS runners have a desktop. Linux runners have none, so the tests and the smoke test run under `xvfb-run`. On a Windows machine, WSL runs the Linux tests, with WSLg as GTK's display.

Tests do not depend on the pixel layout of native controls, which differs between platforms, themes, and DPI settings. They do not show modal dialogs, which would block the run, but create dialogs and inspect them without calling `ShowModal`. Each `Gui.Run` gives up after 10 seconds, and each CI job has a timeout of its own, so a hung test cannot hold a runner for hours.

## Checking accessibility by hand

`AccessibilityInfoTests` read a labeled form through `AccessibilityInfo`, as screen readers read it, on all three platforms, and check that each standard control has its role, its name from the label before it, and its states, so a change that leaves a control unnamed for NVDA, VoiceOver, or Orca fails CI. When checking from .NET, use MSAA or the native UI Automation COM interface. The managed client in `System.Windows.Automation` reports every Win32 control as a pane with no patterns, because it lacks the client-side providers for them.
